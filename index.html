Про мене

Бізнес-аналітик, який опрацьовує вимоги через діаграми. Візуалізуючи вимогу — у флоу-діаграмі чи іншому форматі під конкретну задачу — я розкладаю її на складові й ловлю питання, які легко проґавити на словах: що на межі діапазону, що при відсутніх даних, що при помилці сервера. Закриваю їх ще на етапі аналізу, тож більшість прогалин і потенційних багів знаходиться до розробки, а не після релізу. Підхід не ловить геть усе, але помітно скорочує переробки — і розробники отримують вимоги, готові до реалізації.

Логістика та доставка

Три кейси зростаючої складності — від конфігурованого сервісу розрахунку вартості до наскрізного процесу повернення, що зачіпає клієнтську, складську, логістичну та фінансову зони.

Базовий

Розрахунок вартості доставки

Вартість доставки показувалась приблизно або лише на останньому кроці оформлення, що давало відвал у кошику. Спроєктувала сервіс розрахунку за конфігурованими правилами тарифікації, доступний бізнесу для зміни без релізу.

Що зроблено
  • Модель тарифікації — зона доставки, вага й габарити, сума замовлення, поріг безкоштовної доставки, акційні правила; явно визначений порядок застосування правил.
  • Винесення правил у конфігурацію — бізнес змінює тарифи й пороги через адмінку без участі розробки, оскільки умови перевізників і акції змінюються регулярно.
  • Матриця тарифів — зона × спосіб доставки × вагові ліміти × надбавки, з межовими значеннями для тестування.
  • Продуктова деталь у контракті — поле amountToFreeShipping для підказки «додайте ще на X до безкоштовної доставки» як інструмент зростання середнього чека.
  • Стратегія фолбеку — кешовані тарифи перевізників і резервне правило при недоступності зовнішнього API; оформлення замовлення ніколи не блокується.
  • Вимоги з критеріями — час розрахунку менше 1 секунди для 95% запитів, перерахунок при зміні кошика, приховування недоступних для міста способів.
  • Специфікація API — ендпоінт розрахунку з переліком способів, вартістю та строком доставки.

Результат. Для бізнесу — зниження відвалу на кроці доставки та інструмент керування середнім чеком через поріг безкоштовної доставки. Для системи — конфігурований сервіс тарифікації, незалежний від релізного циклу. Для процесу — прозорі й задокументовані правила замість ручних домовленостей. Метрики: конверсія кошик → замовлення, частка відмов на кроці доставки, середній чек, витрати на безкоштовну доставку.

Середній

Трекінг посилки

Після відправлення клієнт втрачав видимість замовлення, що давало високу частку звернень «де моя посилка». Ускладнення — кілька перевізників, у кожного власний набір статусів, формат даних і спосіб їх віддавати.

Що зроблено
  • Єдина шкала статусів — CREATED → SHIPPED → IN_TRANSIT → AT_DESTINATION_CITY → READY_FOR_PICKUP / OUT_FOR_DELIVERY → DELIVERED, з гілками DELIVERY_FAILED і RETURNING.
  • Таблиця мапінгу — зведення різнорідних статусів перевізників до єдиної шкали; підключення нового перевізника зводиться до конфігурації без зміни клієнтської логіки.
  • Модель отримання оновлень — вебхуки там, де перевізник підтримує, періодичне опитування там, де ні; обґрунтування вибору патерну для кожної інтеграції.
  • Кешування стану — дані клієнту віддаються з власного сховища, а не запитом до перевізника при відкритті сторінки: передбачувана швидкість і незалежність від доступності зовнішнього API.
  • Обробка проблемних сценаріїв — зависла посилка, невдале вручення, повернення відправнику, невідомий статус із fallback і логуванням, кілька посилок в одному замовленні.
  • Правила нотифікацій — визначення ключових переходів, на яких клієнт отримує повідомлення.
  • Специфікація API — вхідний вебхук від перевізника та ендпоінт отримання таймлайну; ідемпотентність обробки повторних оновлень.

Результат. Для бізнесу — зниження частки звернень «де моє замовлення», зростання довіри, менше невдалих вручень. Для системи — окремий сервіс трекінгу з єдиною шкалою; нові перевізники підключаються конфігурацією. Для процесу — прозорий потік від відправлення до вручення, підтримка й клієнт працюють з одним джерелом даних. Метрики: частка WISMO-звернень, охоплення трекінгу, CSAT доставки.

Масштабний

Наскрізне повернення товару

Повернення оформлювалось через дзвінок у підтримку вручну: клієнт не бачив, на якому етапі його гроші, склад отримував неідентифіковані посилки, фінанси проводили повернення із затримками. Спроєктувала процес end-to-end від заявки клієнта до повернення коштів і повернення товару в обіг — із чотирма зонами відповідальності та законодавчими рамками щодо строків.

Що зроблено
  • Наскрізний процес у BPMN — від створення заявки в кабінеті до фінансового проведення; as-is з розривами та to-be з чіткими передачами між зонами.
  • Статусна модель заявки — CREATED → SHIPPED_BY_CUSTOMER → RECEIVED → INSPECTION → APPROVED → REFUNDED, з гілками REJECTED, PARTIALLY_APPROVED, EXPIRED, DISPUTED.
  • Правила права на повернення — перевірка строку, категорії товару та відсутності попереднього повернення; формалізовані спільно з юридичною функцією.
  • Критерії інспекції — матриця оцінки стану товару з обов'язковою фотофіксацією як доказовою базою у спірних випадках, замість рішень на розсуд комірника.
  • Обробка виняткових сценаріїв — часткове повернення з перерахунком долі доставки, некомплектний товар, спірні заявки з ескалацією, протермінування, повернення за нестандартних способів оплати.
  • Ідемпотентність повернення коштів — захист від подвійного повернення як від прямого фінансового збитку.
  • Інтеграція чотирьох зон — особистий кабінет, WMS, API перевізника для зворотної ТТН, платіжний шлюз і ERP; синхронна перевірка права та асинхронна взаємодія з фізичними процесами.
  • SLA між етапами — строк від підтвердженої інспекції до ініціації повернення коштів у межах законодавчих вимог.
  • Декомпозиція епіка — спершу наскрізний потік для повного повернення одного товару з оплатою карткою, далі ускладнення: часткові, спірні, альтернативні способи оплати.

Результат. Для бізнесу — зростання довіри й конверсії за рахунок зняття бар'єру покупки, скорочення ручної роботи підтримки, дотримання законодавчих строків, швидше повернення товару в обіг і менше замороженого капіталу. Для системи — окремий сервіс повернень зі статусною моделлю, правилами й SLA, інтеграція чотирьох зон, фотофіксація як доказова база. Для процесу — прозорість для клієнта, вимірюваність етапів, формалізовані критерії рішень замість ручного розсуду. Метрики: час від заявки до повернення коштів, частка заявок без участі оператора, частка товарів, повернених в обіг придатними.
